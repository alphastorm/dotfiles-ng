# Personal interaction memory

- Long-term memory holds durable personal interaction preferences, never repository content; project decisions, authorization packets, checkpoints, and task state belong in project artifacts. Durable cross-repository workstation, appliance, SSH, or shared OMP-topology facts use memory scope `global`, even when learned in dotfiles; raw transcripts and repo-specific facts stay project-scoped.
- A gate exists only when the next step needs a user decision or authority for an external, privileged, irreversible, or material boundary effect. Routine diagnostics, in-envelope implementation, focused verification, evidence reuse, and retries within declared caps are not gates, and an incomplete checklist, packet, checkpoint, review record, or lifecycle artifact never creates one. At a real gate, MUST invoke Ask before yielding: preselect the safest valid happy path for Enter, include a held/no-effect option when appropriate, and never require the user to copy prose back as authorization.
- `FOUNDER-ONLY / AGENT MUST NOT EXECUTE` overrides Hub and every launcher convention. Ask only authorizes: it MUST name the exact bounded command or effect, and the founder never copies from an Ask preview. Immediately after he selects a command-bearing option, without a reminder, stage that exact non-secret command with `pbcopy` and print the identical command in the next response in a persistent shell-safe code block — especially long or multiline commands; a held/no-effect selection stages nothing. Staging is presentation, not execution: never launch, type, paste, attach to, or automate the command.
- Before staging a founder-run command, run its no-effect validation yourself in the current tree (argument parse, prerequisite preflight, or dry-run; add one when none exists). A staged command that exits immediately in his terminal is an agent defect.
- Every commit and pull request title follows Conventional Commits 1.0.0: `type(scope): description` or `type: description`, with a concise lowercase imperative description.
- Our repositories (carrythroughsystems, alphastorm) land pull requests by squash merge, so the PR title becomes the commit message, plus GitHub's ` (#N)`; never land GitHub's default `Merge pull request #N from …` commit. Keep branch commits only when receipts, tags, or imported history cite their SHAs: fast-forward if the branch is current, otherwise merge with the PR title as the subject. Give a new repository the same settings (`gh api -X PATCH repos/O/R -F allow_merge_commit=false -F allow_rebase_merge=false -f squash_merge_commit_title=PR_TITLE -f squash_merge_commit_message=BLANK`). Others' repositories keep their maintainers' merge method.
- Never ask the founder to review a pull request, add an own-words sentence, or check replies under his account, and never list that review as a step: he reviews every PR after it opens, and upstream instructions to ask the contributor do not apply to him (`rules/upstream-pr-no-sentence-ask.md` enforces this).

## Engineering defaults

- Implementation choice order: reuse existing code or patterns → standard library → native platform capability → installed dependency → minimum new code; stop at the first that fully satisfies the contract.
- Simplification reviews classify findings `delete` | `stdlib` | `native` | `yagni` | `shrink`, each naming the exact location, replacement, preserved behavior, and evidence; net line count is never the objective.
- After a completed, committed implementation package in a repository exposing `bun run cleanse:auto` or `scripts/run_cleanse_lane.sh`, launch the lane once, detached, and report its receipt or `cleanse/auto-*` branch. It is mechanical repair only and enforces its own skip conditions; merging its branch is the founder's decision.
- Use `goal` only for one open-ended objective that needs autonomous continuation across turns — never for bounded retrieval, routine edits, user checklists, or work awaiting a decision. Omit `token_budget` unless the user asks for a cap, and encode observable success, non-goals, verification, and stop conditions.
- Fresh sessions: offer one at a phase boundary (a packet, release, or window is done, or an unrelated objective arrives) or after the second failed attempt on the same hypothesis — never mid-council, mid-window, or while jobs are running, and never force it. Write a resume packet with the objective and next action; repo, branch, and SHA; verified facts kept apart from opinions; failed hypotheses; standing prohibitions; authority grants; and jobs in flight. End the report with its path; the founder resumes with `/new` and "Read <path> and continue" (after `/restart` when upgrading OMP).

## RepoPrompt

- Use only the native RepoPromptCE MCP tools, called through your own eval cells — never `rpce-cli`, shell wrappers, Computer Use, a child Task owner, polling, or an extension-owned job manager. RepoPrompt's file, search, edit, and git tools stay blocked; use the native ones.
- Preparation is top-level-lead only, at most one successful preparation per work package: before the first mutation of design work or technically complex, cross-cutting, multi-repository, predecessor-state-sensitive, or qualification-consequential implementation. Skip it for `NO_CLOUD` material, frozen candidates, diagnostic-red discovery, narrow reproduced fixes, mechanical work, and a work package that already has one. It is context for the accountable lead: it never authorizes, reviews, or accepts.
- Submit once: one JS `eval` cell with `timeout: 0`, so `mcp.json`'s one-hour MCP request deadline owns the wait, holding only this call. `prepare` binds the roots, creates and binds a blank owned tab, builds one Context Builder plan with an export, validates the export, confirms the plan chat is in that tab, and closes the tab unless `keepTab`. It never retries; on failure it throws with the identities known so far and leaves the tab. If it rejects a newer RepoPrompt build's output, inspect that output and fix the helper instead of loosening it.

```js
const { prepare } = await import(`${process.env.HOME}/.omp/agent/lib/repoprompt-preparation.ts`);
return await prepare(tool, { workingDirs: ["/abs/root"], name: "<work package>", instructions: "<task>…</task><context>…</context>" });
```

- A `bg_*` acknowledgement means the cell moved to the background, not that the plan finished. Keep that attempt as the only one; do independent native reads, searches, or scouts that leave the RepoPrompt binding and selection alone; then call `wait` with `{}`, and if another job or message wakes it, handle that and wait again. Never resubmit, `sleep`, poll, reset the JS runtime, or use RepoPrompt `agent_run` for it. A foreground completion is equally valid. No acknowledgement ever authorizes repeating an unresolved preparation or resolver-selected review.
- Consume a succeeded cell only. Its output is the validated plan between two `REPOPROMPT_PREPARATION` identity lines; if OMP spilled it, read `oracle_export_path` with native tools. Cite `chat_id` and `oracle_export_path` and say what you adopt or discard before editing. A failed cell is a failed preparation; never count it. Note the attempt in the work package's existing record: roots and revisions, window, workspace and tab, job ID if any, outcome, and chat and export identity.
- Recovery. An unavailable route permits one retry after a health and routing check, and only while no earlier request can still be in flight. After a local cancel, timeout, or disconnect with an uncertain RepoPrompt outcome, keep the owned tab and identities, inspect only supported diagnostics, and never replay. Since OMP 18.12.4, a cancel or the MCP deadline sends RepoPrompt `notifications/cancelled`, which asks it to stop the builder but confirms nothing, and OMP never resends a call it already sent: after a lost connection that call fails with `retryable: no` and may already have run.
- Revise without rediscovery. When the plan may need revision — the package is headed for critical review, or a council found defects and the fix should close their class — prepare with `keepTab: true`. Later, a `timeout: 0` cell calling `followUp(tool, { contextId, chatId, message, addPaths })` from the same module continues the plan chat: RepoPrompt keeps the earlier turns, including the plan, and rereads the tab's files plus `addPaths` from disk, but `plan` mode sends no diff, so put the findings and the relevant diff in `message`. One send at a time: a second send to the chat cancels the first. A follow-up is context, never another preparation, verdict, or disposition. When the work package closes, `closeTab(tool, { contextId, windowId })`; a closed tab's chat cannot be continued.
- Cleanup: a tab `prepare` reports as `close_refused` or `close_uncertain` stays; report the deferred cleanup. Never set `allow_active`, close another tab or a window, or delete saved workspaces or exports.

## Cloud processing

- Repository work and research are cloud-permitted by default; never infer a separate confidential or local-only class. Only an explicit user, repository, or customer-policy `NO_CLOUD` marker blocks cloud-backed agents; evaluate it before every Task or hosted-reviewer dispatch. On provider or quota failure, use another declared route only while cloud processing remains allowed; otherwise stop without effect.
- Keep the main session on its configured default model; use roles or subagents for alternate models unless the user asks for a bounded main-model experiment.
